# Part 1 — HTTP Basics

HTTP is the **protocol** — the agreed format for how a client (browser) and a server talk to each other.

```
Client  ──── HTTP Request ────►  Server
        ◄─── HTTP Response ────
```

The client asks for a resource; the server processes the request and sends back a response.

## Structure of an HTTP Request

An HTTP request has two main parts, separated by a blank line:

| Part | Purpose |
|---|---|
| **Header** | Metadata about the request — rules of the connection, content type, size, auth, etc. |
| *(blank line)* | Separator between header and body |
| **Body** | The actual payload/content being sent to the server |

Looking at a raw request line by line:

```http
POST /api/users HTTP/1.1        ← Request Line
Host: example.com               ← Request Header Fields
Content-Type: application/json
Content-Length: 44

{"name": "Somchai", "email": "s@mail.com"}   ← Message Body
```

- **Request Line** — the method, the path being requested, and the HTTP protocol version.
- **Header Fields** — key/value pairs describing the request.
- **Message Body** — data sent to the destination (not present on every request).

# Part 2 — HTTP Methods

The method (verb) tells the server *what kind of action* you want to perform on a resource.

## GET — read data

Asks the server for data. Nothing is created or changed.

- Used when fetching data from an API (e.g. a list of all customers, or a single customer).
- The server responds with the requested data.

```http
GET /api/customers HTTP/1.1
```

## POST — create new data

Sends data to the server to **create** a new resource.

- Data travels in the **request body**.
- Classic example: a contact form — you fill in the inputs, press *Send*, and the form data is placed in the request body and sent to the server.
- Sending the same POST several times creates **several new records**.

```http
POST /api/customers HTTP/1.1
Content-Type: application/json

{"name": "Somchai", "email": "s@mail.com"}
```

## PUT — replace / full update

Also sends data to the server, but updates an **entire** resource.

- Replaces **every field** of the existing document/record with the data you send.
- Fields you leave out are typically wiped or reset — not preserved.

```http
PUT /api/customers/1 HTTP/1.1

{"name": "Somchai", "email": "new@mail.com", "phone": "0800000000"}
```

## PATCH — partial update

Updates **only the fields you send**. Any field not included keeps its original value.

```http
PATCH /api/customers/1 HTTP/1.1

{"email": "new@mail.com"}     ← name and phone stay as they were
```

## DELETE — remove data

Deletes the specified resource.

```http
DELETE /api/customers/1 HTTP/1.1
```

## Quick comparison

| Method | Purpose | Has body? | Repeating it |
|---|---|---|---|
| `GET` | Read a resource | No | Same result every time |
| `POST` | Create a new resource | Yes | Creates a **new** record each time |
| `PUT` | Replace a resource entirely | Yes | Same result every time |
| `PATCH` | Update selected fields | Yes | Usually same result |
| `DELETE` | Remove a resource | No | Same end state (resource is gone) |

> **PUT vs POST** — both send data, but repeating a PUT leaves the resource in the same final state, while repeating a POST keeps adding new records. This property is called **idempotency** — see [Part 4](#part-4--idempotency).
>
> **PUT vs PATCH** — PUT replaces the whole record; PATCH touches only the fields you send.

# Part 3 — HTTP Status Codes

The status code in the response tells you whether the request completed successfully. Codes fall into **five groups**:

| Range | Group | Meaning |
|---|---|---|
| `1xx` | Informational | Request received, process continuing |
| `2xx` | Successful | The request succeeded |
| `3xx` | Redirection | Further action needed; resource moved |
| `4xx` | Client Error | Something is wrong with the request |
| `5xx` | Server Error | The server failed to fulfil a valid request |

## 1xx — Informational (100–199)

Interim responses that carry information about the request while it is still being processed.

## 2xx — Successful (200–299)

| Code | Name | Meaning |
|---|---|---|
| `200` | OK | The request succeeded. The most commonly seen code. |
| `201` | Created | A new resource was created (typical response to POST). |
| `204` | No Content | Success, but there is no body to return. |

## 3xx — Redirection (300–399)

| Code | Name | Meaning |
|---|---|---|
| `301` | Moved Permanently | The resource now lives permanently at another URL. The new URL should be given in the response. |
| `302` | Found | The resource has been moved to a new location **temporarily**. |

## 4xx — Client Error (400–499)

| Code | Name | Meaning |
|---|---|---|
| `400` | Bad Request | The server cannot understand the request. |
| `401` | Unauthorized | No valid authentication credentials were supplied for the target resource. |
| `403` | Forbidden | The user is authenticated but not allowed to perform this action. |
| `404` | Not Found | No resource exists at the requested URL. *(The one you'll meet most often.)* |
| `405` | Method Not Allowed | That request method isn't permitted on this resource. |

> **401 vs 403** — 401 means "we don't know who you are"; 403 means "we know who you are, and you may not do this."

## 5xx — Server Error (500–599)

| Code | Name | Meaning |
|---|---|---|
| `500` | Internal Server Error | The server hit an unexpected condition and couldn't complete the request. |
| `503` | Service Unavailable | The server is temporarily unavailable — usually overload or maintenance. |
| `504` | Gateway Timeout | The server, acting as a gateway or proxy, didn't get a response from the backend server in time. |

# Part 4 — Idempotency

## Why it matters — the unhappy path

When designing an API it's easy to only think about the **happy path**. A robust API also has to survive the unhappy one:

- The user's internet drops right after the request is sent.
- The server is under load and the client times out before a response arrives.

In both cases the client **retries** — either automatically, or because a frustrated user keeps hitting *Submit*. If several of those requests get through, you end up with **duplicates**.

How bad that is depends on the operation:

| Operation | Duplicate is... |
|---|---|
| Posting a blog comment | Annoying, not fatal |
| Sending an email | Bad — recipients get multiple copies |
| Charging a card | **Very bad** — customer charged twice, or ten times |

Idempotency is how you protect the operations in the bottom rows.

## Definition

> A request method is **idempotent** if the intended effect on the server of multiple identical requests is the same as the effect of a single such request.

In short: calling the API N times leaves the server in the same state as calling it once.

**Note:** idempotent ≠ same response body every time. It's about the **effect on the server state**. A second `DELETE` may return an error, but the server state is unchanged — so `DELETE` is still idempotent.

## Idempotency of HTTP methods

| Method | Idempotent? | Why |
|---|---|---|
| `GET` | ✅ Always | Read-only. Nothing is created or updated. |
| `PUT` | ✅ Always | Full replace. Updating a user's email 5 times leaves the same final value. |
| `DELETE` | ✅ Always | After the first call the object is gone; further calls don't change server state (they may just error). |
| `PATCH` | ⚠️ Depends | Fine if you're just setting a field (`email = x`). **Not** idempotent if used for operations like copy / move / add / remove. |
| `POST` | ❌ Generally not | Creates something new. Calling it N times generally creates N resources. |

### Why POST is the problem case

**Case A — the resource has a natural unique key.**
Creating a user with a unique username: the first request succeeds, the second fails with "user already exists." Server state only changed once. But the UX is bad — if the user lost connection on request #1 and retried, they're told the username is taken when *they* are the ones who took it.

**Case B — no unique identifier at all.** This is the dangerous one:

```json
POST /payments
{
  "amount": 2000,
  "currency": "thb",
  "source": "card_xxx"
}
```

Nothing in this body links it to a specific purchase. A payment platform receiving two of these has no way to know it's a retry — it just charges the customer twice.

## Making POST and PATCH idempotent

For operations that must happen **exactly once** (payments, sending email), you need to add idempotency yourself. The only real way is a **unique identifier per logical operation**.

### Where the key comes from

1. **An ID you already have** — e.g. a saved basket has an ID that is unique to that order. Use it as the idempotency key.
2. **A hash of the request body** — workable, but only if the same user could never legitimately send an identical request. If someone orders a SpongeBob beach towel and orders another one 30 seconds later, that's not a duplicate — they might just really like SpongeBob.
3. **A client-generated key sent in a header** — the standard approach. Stripe uses a header called `Idempotency-Key`, but the name is up to you.

```http
POST /payments HTTP/1.1
Idempotency-Key: 4f3d9c1a-8b2e-4f7a-9c11-1d2e3f4a5b6c
Content-Type: application/json

{"amount": 2000, "currency": "thb"}
```

### Make the key globally unique

A user-supplied key is **not** guaranteed to be globally unique — two users could send the same key, or the same user could reuse a key across different endpoints. So always build your stored key from a combination:

```
storage_key = idempotency_key + user_id + api_path
```

## Storage

Store the combined key **together with the successful response** you returned.

When a request arrives with a key you've already seen, don't perform the operation — just replay the stored response. From the user's point of view the operation succeeded; they never need to know it's a replay.

**Use a key-value store** such as Redis or DynamoDB.

**Don't use in-memory storage** (e.g. a dictionary), because:

- With multiple API instances behind a load balancer, each instance can't see the other instances' keys.
- All keys are lost on application restart.

## Workflow

```
Request arrives with idempotency key
            │
            ▼
   Key exists in storage?
      │             │
     Yes            No
      │             │
      ▼             ▼
 Return stored   Perform the operation
   response             │
                        ▼
                   Successful?
                        │ Yes
                        ▼
              Store key + response
                        │
                        ▼
                Return response
```

## How long to keep keys

Depends entirely on the application:

| Scenario | Suggested TTL |
|---|---|
| Just guarding against double-clicks | ~10 minutes |
| A retry mechanism is in place | Longer |
| Typical general-purpose default | **24–48 hours** |

If you're using Redis or DynamoDB, set a **TTL** so keys are deleted automatically.

## Idempotency validation

Normally: same key + same user + same endpoint ⇒ assume it's the same request, replay the stored response.

But the user might have **reused a key by mistake** while sending a genuinely different body. To guard against that:

1. Store a **hash of the request body** alongside the idempotency key.
2. On a repeat key, compare the incoming body's hash to the stored one.
3. If they don't match, **return an error** instead of replaying.

## Implementation note (.NET Core)

- Use the **distributed caching** library and store keys in Redis.
- Create a **filter** and apply it to the endpoints that need idempotency.
- The `IdempotentAPI` NuGet package handles most of this for you.

> The same pattern maps directly to other stacks — middleware/interceptor + Redis works the same way in Express, FastAPI, or Spring.

# Part 5 — Request / Response Lifecycle

What actually happens between clicking a button and seeing the result — traced through the architecture of a modern web application.

## Overview

```
Browser
   │  1. DNS resolution
   ▼
DNS (Route 53)
   │  2. resolved IP
   ▼
CDN (CloudFront)  ──► static assets served from edge cache
   │
   ▼
WAF               ──► malicious traffic blocked here
   │
   ▼
Nginx (optional)  ──► reverse proxy, SSL termination
   │
   ▼
Load Balancer (NLB / ALB)
   │
   ▼
API Gateway       ──► authN/authZ, rate limiting, routing
   │
   ▼
Backend Services (EC2 / Lambda / Kubernetes)
   │           │
   ▼           ▼
Database    Message Queue (Kafka / SQS)
(PostgreSQL / DynamoDB)
```

The response then travels back along a similar path.

## 1. DNS Resolution

The user types `example.com`. DNS acts as the **internet's phone book**, translating the domain name into an IP address.

- That IP may point at a **load balancer** or a **CDN distribution**, depending on the architecture.
- Fast DNS resolution matters because it directly affects **initial load time**.
- A service like **AWS Route 53** can direct the user to the **closest available server**, so routing is fast and efficient.

## 2. CDN (Content Delivery Network)

A CDN such as **AWS CloudFront** caches **static assets** — images, videos, CSS — at **edge locations** physically closer to the user.

| Benefit | Detail |
|---|---|
| Lower latency | Content is served from a nearby edge, not the origin |
| Faster loads | Especially for users spread across regions |
| Lower cost | Offloads requests from your main server, particularly under global traffic |

> Even a **1-second delay** can cause users to drop off — speed is not a nice-to-have.

## 3. WAF (Web Application Firewall)

Before the request reaches your backend, it passes through the WAF — your application's **first line of defence**.

It filters out **malicious traffic before it hits backend services**, stopping attacks such as:

- **SQL injection**
- **Cross-site scripting (XSS)**

## 4. Nginx — Reverse Proxy

Nginx sits in front of your services as a **reverse proxy**:

- Routes traffic
- Handles **SSL termination**
- Caches **dynamic** content

**Is it required?** No — it's **optional** in many architectures, because CloudFront and the ALB already cover much of this. Add Nginx when you need **fine-grained control** over routing, caching, or SSL termination.

## 5. Load Balancer

Distributes incoming traffic across multiple backend servers to keep the system **available**.

### NLB vs ALB

| | **NLB** (Network Load Balancer) | **ALB** (Application Load Balancer) |
|---|---|---|
| OSI layer | Layer 4 — Transport | Layer 7 — Application |
| Routes on | IP address + port | HTTP/HTTPS content — paths, host names, headers |
| Inspects request content? | No | Yes |
| Protocols | TCP, UDP | HTTP / HTTPS |
| Best for | Extreme performance: gaming, financial services, real-time apps | Web apps, REST APIs, microservices |
| Strength | Millions of requests/sec at very low latency | Advanced routing rules |

**ALB routing examples:**

```
/api/users      →  user service
/api/products   →  product service

example.com/api     →  backend API service
example.com/static  →  static content service
```

## 6. API Gateway

Acts like a **traffic cop** in front of your services:

- **Validates** the request
- **Authorizes** the user
- Enforces **rate limiting and throttling** — so no single client can overwhelm the system
- **Routes** the request to the correct backend: an EC2 instance, a Lambda function, or a microservice running in Kubernetes

## 7. Backend Services

This is where the heavy lifting happens. In a **microservices architecture**, each service owns one specific function — e.g. one handles authentication, another processes payments.

**Why split it up:**

- Teams work **independently**
- Services **scale separately** from each other
- Updates ship **without impacting the entire system**

## 8. Database Layer

Where persistent data lives — the heart of the application.

| Type | Example | Best for |
|---|---|---|
| **NoSQL** | DynamoDB | Distributed apps that scale dynamically; flexible / unstructured data |
| **SQL** | PostgreSQL | Structured, relational data |

### Message Queues

For **asynchronous** work, the request is handed to a queue such as **Kafka** or **SQS**. These handle tasks that don't need immediate processing:

- Email notifications
- Background jobs

The user gets their response without waiting for these to finish.

## 9. Supporting Layers

| Layer | Tools | Purpose |
|---|---|---|
| **Authentication** | OAuth 2.0, OpenID Connect, JWT | Verify who the user is |
| **Caching** | Redis, Memcached | Cache frequently requested data, reducing backend load |
| **Monitoring** | Prometheus, AWS CloudWatch | Track metrics, catch issues before they escalate |

## 10. The Response Journey

The trip back matters just as much as the trip in, and follows a similar path:

1. The processed response goes back to the **API Gateway**, which may apply **formatting or transformations** before routing it onward.
2. The **load balancer** routes the response back to the user, balancing outgoing traffic if needed.
3. Any **static content** in the response — images, cached data — can be served **directly from a CDN edge location** to minimise latency.
4. The response reaches the **browser or mobile app**, which renders the data.

The cycle is complete. In a well-designed system, this whole journey happens in **milliseconds**.

# Cheat Sheet

## Methods

```
GET    →  read
POST   →  create        (repeat = duplicates)
PUT    →  replace all   (repeat = same result)
PATCH  →  update some fields
DELETE →  remove
```

## Status codes

```
1xx  →  info
2xx  →  it worked
3xx  →  look somewhere else
4xx  →  your fault
5xx  →  server's fault
```

## Idempotency

```
Idempotent      GET, PUT, DELETE        (and HEAD, OPTIONS)
Depends         PATCH
Not             POST

Need exactly-once?  →  Idempotency-Key header
Storage key         =  key + user_id + api_path
Store               =  key → saved response  (Redis / DynamoDB, TTL 24–48h)
Never store keys in memory
```

## Lifecycle

```
REQUEST  →  DNS → CDN → WAF → Nginx → LB → API Gateway → Service → DB/Queue
RESPONSE →  Service → API Gateway → LB → (CDN for static) → Browser

DNS         name → IP, route to nearest region
CDN         cache static at the edge
WAF         block SQLi / XSS before backend
Nginx       reverse proxy, SSL termination   (optional)
NLB  = L4   IP + port,     ultra low latency
ALB  = L7   path + host,   web apps & microservices
Gateway     authZ + rate limit + route
Async       Kafka / SQS for email, background jobs
```
